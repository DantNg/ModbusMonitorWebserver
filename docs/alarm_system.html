Hệ thống Alarm – Flask Modbus Monitor

Tài liệu kỹ thuật chi tiết về cấu trúc và logic hoạt động của hệ thống cảnh báo (alarm). Dựa trên workers/alarm_worker.py, workers/alarm_strategies.py, shared/engine/ và static/js/subdashboard-detail.js.

1. Tổng quan

Hệ thống alarm chạy trong một process độc lập (orchestra_alarm.py → AlarmWorker), tách biệt với web server và modbus worker. Cứ mỗi 1 giây (check_interval), worker đọc giá trị tag mới nhất từ DB, đánh giá điều kiện, và phát sự kiện qua Socket.IO để trình duyệt cập nhật màu sắc real-time.

Tag Alarm — cảnh báo theo từng tag riêng lẻ Card Alarm — cảnh báo theo card hiển thị (PV vs ngưỡng) Quad Alarm — biến thể của Card cho quad card
Nguyên tắc cốt lõi: Worker emit Socket.IO trước để UI cập nhật tức thì, ghi DB sau (chậm hơn nhưng UI đã đổi màu xong). Mọi state thay đổi đều tuân theo stable time (thời gian ổn định) để chống nhiễu/chống nhấp nháy.

3. Tiến trình & vòng lặp chính

Entry point: create_alarm_worker_process() tạo một multiprocessing.Process chạy AlarmWorker.run(). Khi khởi động:

run() → set running=True
↓
Khởi động command_handler thread (nhận stop/reload/get_status) + SMS sender thread (serialize COM port)
↓
_restore_card_alarm_states() — đọc lại các alarm đang active từ DB (card + quad) vào dict in-memory, tránh "mất màu" sau restart
↓
_alarm_loop() — vòng lặp vô hạn mỗi check_interval=1.0s

3.1. Mỗi chu kỳ của _alarm_loop()

1. _tag_value_cache.clear() — xóa cache giá trị tag (per-cycle, tránh query trùng trong 1 cycle)
↓
2. Mỗi 10 cycle (~10s): health-check Socket.IO; nếu mất kết nối → reconnect trong background thread
↓
3. _load_alarm_rules() — load rules từ DB (cache TTL 10s, enrich tag_name/device_name)
↓
4. _process_alarm_rules_v2() — đánh giá toàn bộ alarm_rules qua engine v2
↓
5. _evaluate_card_conditions() — đánh giá tất cả card + quad conditions qua Strategy Pattern
↓
6. Mỗi 10 cycle: cập nhật shared_state["alarm_worker_status"] (active_alarms, total_rules, sio_connected)
↓
7. time.sleep(check_interval)
Caching nhiều lớp để giảm tải DB: alarm rules (TTL 10s), card conditions (5s), quad conditions (5s), card info (30s), tag transform scale/offset (60s), device status (3s), managed tag IDs (10s). Giá trị tag dùng per-cycle cache (xóa đầu mỗi vòng).

4. Tag Alarm — luồng v1 (_process_alarm_rule)

Đây là logic gốc cho từng alarm_rules (giờ là fallback khi engine v2 không khả dụng). Một rule gồm: target (tag_id), operator (> < >= <= == !=), threshold (số đơn hoặc "min,max" cho between/not_between), level, on_stable_sec, off_stable_sec, email, sms.

# Lõi đánh giá điều kiện
def _evaluate_alarm_rule(self, rule, tag_value):
    operator = rule["operator"]; threshold = float(rule["threshold"])
    return self._compare_value(tag_value, operator, threshold)

# Giá trị tag đọc từ tag_latest_values — ĐÃ là engineering units (raw×scale+offset)
# nên KHÔNG nhân scale/offset lần nữa.

Logic chuyển trạng thái (rút gọn):

Điều kiện hiện tạiState trướcHành động
metinactiveBắt đầu đếm on_stable_sec. Khi đủ → set active, emit INCOMING, ghi alarm_events, gửi notification, reset timer
not metactiveBắt đầu đếm off_stable_sec. Khi đủ → set inactive, emit OUTGOING, ghi event, gửi clear notification, reset timer
met == state—Không transition → _alarm_since.pop() (reset timer ổn định)
Sau khi INCOMING fire, _alarm_since được reset để OUTGOING đếm từ lúc condition thực sự clear — không phải từ lúc on_stable bắt đầu (quan trọng khi on_stable ≥ off_stable).

5. AlarmEvaluator v2 shared/engine

Engine mới thay thế vòng lặp _process_alarm_rule cho bảng alarm_rules. Card alarm không dùng engine này.

5.1. Quy trình _process_alarm_rules_v2()

1. Lọc bỏ rule disabled
↓
2. Pre-fetch giá trị mọi tag → điền _tag_value_cache một lần
↓
3. Tính rules_hash (id, on/off_stable, threshold, operator, enabled). Nếu đổi → translate_alarm_rules_table() + set_rules() để re-sync evaluator
↓
4. Build signal_map = {tag_id → Signal(value, timestamp)}
↓
5. v2_evaluator.evaluate(signal_map) → trả về danh sách AlarmEvent
↓
6. Mỗi event → _handle_v2_alarm_event(): emit socket + ghi DB + notification

5.2. Xử lý event v2

_handle_v2_alarm_event() chỉ xử lý 2 transition: is_alarm_on (→ALARM) và is_alarm_off (ALARM→NORMAL). Các state PENDING_ON/PENDING_OFF bị bỏ qua (StabilityTracker xử lý nội bộ).

Bug đã xử lý (xem memory): socket title của INCOMING và OUTGOING trước đây khác nhau (INCOMING dùng "Alarm Triggered: {name}", OUTGOING dùng device_name) → tạo notification trùng "ma" trên chuông. Nay thống nhất title = rule_name cho cả hai chiều.

5.3. Seed state sau khởi động

_restore_v2_tag_alarm_states() chạy một lần sau lần sync rules đầu tiên: với các rule còn stale INCOMING trong DB (chưa có OUTGOING tương ứng), nó seed evaluator vào state ALARM. Lần evaluate kế tiếp, nếu condition không còn met → off_stable timer chạy → fire OUTGOING → dọn sạch DB. Tránh alarm "kẹt active" vĩnh viễn sau restart.

v1 vẫn được giữ nguyên (chạy shadow / fallback) — không xóa code v1.

6. Card Alarm — đánh giá theo cột

Mỗi card hiển thị 1–2 cột (left/right). Với mỗi cột, condition gồm HIGH và LOW threshold độc lập, mỗi cái có operator, value/compare_tag, on_stable, off_stable riêng.

6.1. _process_card_condition() → _evaluate_card_column()

# Tham số condition cho 1 cột (column = "left"/"right")
{column}_high_operator        # > < >= <=
{column}_high_compare_type    # "static" | "tag"
{column}_high_value           # ngưỡng tĩnh
{column}_high_compare_tag_id  # ngưỡng động (giá trị tag khác)
{column}_high_on_stable / _off_stable
# ... lặp lại y hệt cho {column}_low_*

Các bước đánh giá 1 cột:

1. Offline check: nếu device của PV/SV/compare-tag offline → bỏ qua, đánh dấu _offline_skipped. Khi online lại → re-emit INCOMING (reconnect path)
↓
2. Eval HIGH: lấy threshold (static value hoặc value của compare tag) → _compare_value(pv_value, high_op, high_threshold)
↓
3. Eval LOW: tương tự với low_op
↓
4. alarm_triggered = high_met OR low_met; current_alarm_type = "High" if high_met else ("Low" if low_met else None)
↓
5. Chọn stable times tương ứng với type đang/ sẽ active → gọi _process_card_alarm_state()
Chỉ PV value được so sánh với ngưỡng. SV (setpoint) chỉ để hiển thị, không tham gia logic alarm (trừ khi SV được cấu hình làm compare tag động).

8. State Machine — _process_card_alarm_state()

Đây là trái tim của card alarm. Các dict tracking in-memory (key = alarm_key):

DictÝ nghĩa
_alarm_statesalarm_key → đang active (True/False)
_alarm_typesalarm_key → "High"/"Low" (hướng đang active)
_alarm_sincealarm_key → timestamp bắt đầu đếm stable
_pending_alarm_typealarm_key → type mà timer on_stable đang đếm cho
_alarm_last_evalalarm_key → lần evaluate gần nhất (continuity guard)
_offline_skippedalarm_key bị skip do device offline (để re-emit khi reconnect)

8.1. Bốn nhánh xử lý

🔄 Nhánh A — Alarm TYPE CHANGED (HIGH↔LOW khi đang active)
Điều kiện: previous_active AND current_condition AND stored_type ≠ current_type.
  1. Emit OUTGOING cho type cũ
  2. Xóa DB state cũ (để periodic sync không re-apply màu cũ)
  3. Reset _alarm_since = now, set _alarm_types = current_type
  4. return — bắt đầu đếm on_stable cho type mới
⬆ Nhánh B — INCOMING (condition met, chưa active)
Quản lý _pending_alarm_type:
  • Chưa có timer → bắt đầu _alarm_since=now, ghi pending type
  • pending_type ≠ current_type (đổi loại trong khi đếm) → reset timer, đếm lại cho type mới
Khi stable_time ≥ on_stable_sec: set active, set type, reset timer ngay (để off_stable đếm từ lúc clear), emit INCOMING, ghi alarm_events + card_alarm_states, gửi notification.
⬇ Nhánh C — OUTGOING (condition hết, đang active)
Khi stable_time ≥ off_stable_sec: lấy alarm_type từ dict (KHÔNG default "High" — nếu thiếu → log warning & skip), set inactive, emit OUTGOING với threshold/operator đã lưu, ghi event, xóa DB state, gửi clear notification, pop toàn bộ tracking key.
⏸ Nhánh D — Stable (condition == state, không transition)
Reset _alarm_since + _pending_alarm_type. Nếu vừa reconnect mà vẫn đang active → re-emit INCOMING để UI khôi phục màu (device offline làm UI mất màu).

9. Stable Time — cô lập HIGH và LOW

Mỗi alarm có on_stable_sec (giữ condition đúng bao lâu trước khi trigger) và off_stable_sec (giữ clear bao lâu trước khi tắt). HIGH và LOW dùng timer độc lập.

Cơ chế cô lập: dùng _pending_alarm_type[alarm_key]. Khi đang đếm on_stable cho HIGH mà condition chuyển sang LOW → pending_type ≠ current_type → reset _alarm_since, bắt đầu đếm lại cho LOW. Tránh việc thời gian "tích" của HIGH bị dùng nhầm cho LOW.
# Trích _process_card_alarm_state — nhánh INCOMING
pending_type = self._pending_alarm_type.get(alarm_key)
if alarm_key not in self._alarm_since:
    self._alarm_since[alarm_key] = now
    self._pending_alarm_type[alarm_key] = current_alarm_type
elif pending_type != current_alarm_type:        # đổi loại khi đang đếm
    self._alarm_since[alarm_key] = now            # RESET timer
    self._pending_alarm_type[alarm_key] = current_alarm_type
Checklist khi stable time bị "mix" HIGH/LOW
INCOMING: nếu pending_type ≠ current_type → phải reset _alarm_since
Khi INCOMING fire → pop(_pending_alarm_type)
Khi OUTGOING fire → pop(_pending_alarm_type)

10. Edge cases & bảo vệ

10.1. Continuity guard (chống trigger tức thì)

Vấn đề: nếu một alarm_key không được evaluate nhiều cycle liên tiếp (card bị xóa/disable rồi xuất hiện lại, hoặc card_id được DB cấp lại sau khi MySQL restart), timestamp _alarm_since cũ khiến stable_time = now − old_ts rất lớn → alarm trigger ngay lập tức, bỏ qua stable time.
last_eval = self._alarm_last_eval.get(alarm_key)
gap_limit = max(5.0, 3.0 * check_interval)
if last_eval and (now - last_eval) > gap_limit:
    # phát hiện gap → reset countdown, đếm lại từ đầu (luôn an toàn)
    self._alarm_since[alarm_key] = now
    self._pending_alarm_type.pop(alarm_key, None)

10.2. Prune stale tracking

_prune_stale_card_alarm_tracking() mỗi cycle xóa các tracking key của card/quad không còn active (không nằm trong _collect_live_card_alarm_prefixes()). Chỉ đụng key dạng card_*/quad_*, KHÔNG đụng tag alarm (key là int rule_id). Đảm bảo key tái sử dụng luôn bắt đầu sạch.

10.3. Managed tag IDs (chống trùng cảnh báo)

_get_all_managed_tag_ids() thu thập các PV tag đang được card condition quản lý (chỉ cột có high_operator hoặc low_operator). Mục đích: tránh trùng giữa card alarm và legacy tag alarm. Lưu ý: chỉ suppress PV tag của cột có condition — SV tag và cột chưa cấu hình KHÔNG bị suppress (tránh chặn nhầm legacy alarm).

10.4. Device offline / reconnect

Nếu device offline → skip cột, ghi vào _offline_skipped. Khi device online lại (reconnected=True) và alarm vẫn đang active → re-emit INCOMING để UI khôi phục màu đỏ/vàng.

10.5. Restore sau restart

_restore_card_alarm_states() đọc get_active_card_alarms() + get_active_quad_alarms(), build đúng alarm_key qua strategy.make_alarm_key(), set lại _alarm_states + _alarm_types. Worker tiếp tục từ trạng thái trước đó thay vì coi mọi thứ là mới.

14. Notification (Email / SMS)

Tag alarm lấy contacts từ field email/sms của rule; card alarm lấy từ {column}_email/{column}_sms. Tách bằng dấu phẩy/chấm phẩy/khoảng trắng/xuống dòng, khử trùng.

  • Email: gửi trong thread riêng (non-blocking), SMTP starttls (config SMTP_config.json)
  • SMS: đưa vào sms_queue → một thread sender duy nhất serialize truy cập COM port (GSM/AT commands), tự chọn GSM 7-bit hoặc UCS2, có chunk + retry +CMS ERROR 305
  • Debounce: _should_send_notification() = max(5s, 2×stable_time) giữa 2 lần gửi cùng loại
Strip device prefix: _strip_device_prefix() bỏ prefix [TEST] ở đầu tên card để title notification của card alarm thống nhất với legacy tag alarm (tránh entry chuông trùng "ma").
